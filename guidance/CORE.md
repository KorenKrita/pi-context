## 上下文管理工具

你的上下文不是流水账，而是工作台：留有用的，收走用完的。三个工具帮你做这件事：

- **`acm_checkpoint`** — 存档。给当前位置起个名字，瞬间完成，不改变上下文。
- **`acm_timeline`** — 查看。当前上下文、存档、全树搜索、分支结构，附带用量。
- **`acm_travel`** — 折叠。回到之前某个点，把那之后的历史换成一份交接单。上下文变小；原始历史留在会话树里，随时可回去。

**什么时候折**：一段工作只剩结论有用、过程不再需要的时候。调试收尾、读完一批文件、新请求只依赖之前的结果——都是折叠点。检验方法只有一条：不回头重读，能把这段写成一份具体的交接单，就可以折；写出来含糊，说明还没消化完，先不折。

工具结果末尾的 `[ctx 51% used · fold→22%]` 是当前用量和折掉上一段后的预计用量。数字只是参考，折不折由上面那条检验说了算。

**交接单**：`goal`（在做什么）、`state`（知道什么，含接下来要用的具体值）、`next`（下一步做什么）必填；`evidence`（证据指针）、`external`（外部副作用）、`exclusions`（排除过的方向）、`recover`（找回历史的存档）用到才写。合格标准：没看过前文的人只读它就能接着干。

简单情况——读完代码开始动手，过程折掉：

```json
{
  "goal": "给 parser 加上嵌套注释支持",
  "state": "入口是 src/parser.ts:parseComment（88 行），现在不处理嵌套；测试在 test/parser.test.ts",
  "next": "用深度计数改写 parseComment，跑 bun test test/parser.test.ts"
}
```

复杂情况——排查到一半折掉前半程，假设和排除项必须带上：

```json
{
  "goal": "找出 v2.3.0 后 checkout p99 延迟翻倍的原因",
  "state": "数据库已排除（查询耗时与 7-01 基线持平）。剩两个嫌疑：连接池耗尽（证据弱）、payments 新加的重试循环（v2.3.0 引入，未验证）。关键值：池上限 50（config/prod.yaml:23）；重试代码 commit 9f31c2a",
  "next": "读 services/payments/client.ts 的重试循环，对照池上限 50 检查退避参数",
  "evidence": "dashboards/checkout-p99.json；git log v2.2.0..v2.3.0 -- services/payments",
  "exclusions": "数据库索引确认健康，不用再查",
  "recover": "latency-scan"
}
```

写成"排查了延迟问题，排除了一些方向，继续看"就是不合格——假设、证据、关键数值全丢了，接手的人干不了活。

**拓展：回去取细节**。折叠不是删除。发现缺一个已折叠的细节（某段报错原文、某个精确数字），先 `acm_checkpoint` 存下当前位置，travel 到旧分支拿到细节，再 travel 回来——交接单里带上取回的内容就行。整个来回只花两次折叠，比重新推导便宜得多。

**折叠之后**：回执 applied 就直接执行 next，不要回头重读折掉的内容。travel 只改对话上下文；文件、进程、外部系统都保持原样。
